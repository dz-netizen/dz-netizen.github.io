差分信号技术

引入原因

差分信号不是看某一根线对地的绝对电压，而是看两根线之间的电压差：$V_{diff} = V_p - V_n$
核心优势：

  1. 抗共模噪声强
    外部噪声通常会同时耦合到两根线上，接收端做相减后，共同出现的噪声会被抵消。
  2. EMI(电磁干扰) 更低
    差分对中两根线电流大小相等、方向相反，远场辐射相互抵消，比单端信号更容易控制电磁干扰。
  3. 低摆幅也能可靠传输
    LVDS 典型差分摆幅只有几百 mV，但接收器只关心差分电压，因此速度快、功耗低。
  4. 适合高速长距离互连
    高速 SerDes、PCIe、以太网、CML/LVDS/LVPECL 等常用差分，是因为 GHz 级信号对噪声、串扰、反射、地弹都很敏感。

主流差分技术

在选择高速差分信号技术时有很多选择。不同的技术通常共享某些特性，但在性能、功耗和目标应用程序方面差异很大

LVDS(Low-Voltage Differential Signaling)：低电压差分信号
CML（Current Mode Logic）：当前模式逻辑
LVPECL(Low Voltage Positive Emitter Coupled Logic) 低电压正射极耦合逻辑。

LVDS驱动器和接收器

驱动器中含有一个3.5mA的电流源。因为接收器的输入阻抗很高，故整个电流实际上全部流过100Ω的终接电阻，于是在接收器输入端产生了350mV的电压。接收器的阈值可以保证为100mV或更低，可在0V-2.4V的宽共模范围内维持这样的灵敏度水平，提供出色的噪声裕量。

serdes的引入

并行总线接口

在SerDes流行之前,芯片之间的互联通过系统同步或者源同步的并行接口传输数据

随着接口频率的提高，在系统同步接口方式中, 有几个因素限制了有效数据窗口宽度的继续增加。

  • 时钟到达两个芯片的传播延时不相等(clock skew)
  • 并行数据各个bit的传播延时不相等(data skew)
  • 时钟的传播延时和数据的传播延时不一致(skew between data and clock)
    虽然可以通过在目的芯片内用PLL(Phase Locked Loop)补偿时钟延时差(clock skew)，但是PVT(process,voltage,temperature)变化时，时钟延时的变化量和数据延时的变化量是不一样的。这又进一步恶化了数据窗口。

源同步解决了“时钟和数据不同步”的问题，但还是存在“引脚数量、传输速率”等问题

串行化

引入串行化主要是为了解决并行总线在高速下的问题：

  1. 减少引脚数量
    例如 32-bit 并行总线至少需要 32 根数据线，还可能需要时钟、控制、校验线。串行化可以用一对或几对差分线完成传输。
  2. 避免 data skew
    并行总线中每一根 bit 线长度、负载、延迟不同，高速下 bit 之间会错位。串行链路只有一条数据流，不存在多 bit 同时到达的问题。
  3. 时钟可以嵌入数据流
    串行化可以通过编码保证数据跳变，接收端用 CDR 恢复时钟。
  4. 更容易做均衡和通道补偿
    高速串行链路可以使用预加重、去加重、CTLE、DFE 等技术补偿 PCB、封装、连接器、背板损耗。

serdes

SERDES将发送端多路低速并行信号转换成高速串行信号，经过传输媒体(光缆或铜线)，最后在接收端高速串行信号重新转换成低速并行信号。这种点对点的串行通信技术充分利用传输媒体的信道容量，减少所需的传输信道和器件引脚数目，提升信号的传输速度，从而大大降低通信成本。

serdes（serializer/deserializer）架构

并行时钟serdes

并行时钟serdes通常对“数据-地址-控制”并行连接的总线进行串行化。

采用了复用器处理

嵌入式时钟位serdes

时钟位嵌入式架构中的发送器将数据总线上的数据信号和时钟串行化，形成单路串行信号对。

两个时钟位，一路高而另一路低，被嵌入到串行流中，用于界定每个字的起点和终点，并在串行数据流中产生一个周期性的上升沿。

优点：数据有效负载的字宽度无需被限制为字节的倍数，10/16/18/24 bit是常见的总线宽度。
无论有效负载的数据样式如何变化，解串器都可以从串行数据流中将数据恢复出来，在接收器不受系统直接控制的远程模块的系统中，这种自同步能力是一项极为有用的功能。
同时因为接收器可以锁定到接收的嵌入时钟上，而不是锁定到外部的基准时钟信号上，因此对于发送器和接收器的时钟信号抖动要求可以大大放宽。

8b/10b serdes

8-bit/10-bit 串化器可将每个并行数据字节映射为一个10bit的代码，然后将该10bit码串行化，传送到一个串行对上。

10bit传输码特点：可以确保每个周期内多次边沿切换，使得接收器能与输入数据流实现同步，
并实现直流平衡（所发送的0和1的数量相平衡），使得对于交流耦合负载、光电模块等的驱动成为可能。
8b/10b serdes架构使用外部基准时钟来恢复时钟信号，并对数据流进行解串处理，因此需要严格的基准时钟源频率以及抖动控制。

I2C

I2C（Inter-Integrated Circuit）是一种多主机、两线制、低速串行通信总线，广泛用于微控制器和各种外围设备之间的通信。

  • 两线制总线：I2C仅使用两条线——串行数据线（SDA）和串行时钟线（SCL）进行通信，有效降低了连接复杂性。
  • 多主多从设备支持：I2C支持多个主设备和多个从设备连接到同一总线上。每个设备都有唯一的地址。
  • 阻塞传输：I2C支持阻塞传输机制，即主设备可以在传输过程中控制总线，防止其他设备发送数据。

开漏(open drain)结构只能拉低。高电平靠上拉电阻。
优点：多个设备可以共享。缺点：慢。

为啥GAP

这组 ILA 是用来同时观察 GTY 物理状态、selftest 状态机、TX/RX packet 流、PCS lock、错误计数 的。

probe1: GTY reset / power 状态

.probe1({gt_powergood, gt_txresetdone, gt_rxresetdone,
gt_txpmaresetdone, gt_rxpmaresetdone})

含义：看 GTY 底层是否 ready。

大概字段：

gt_powergood[3:0] 每条 GTY lane 电源/primitive ready
gt_txresetdone TX reset 流程完成
gt_rxresetdone RX reset 流程完成
gt_txpmaresetdone[3:0] 每条 lane TX PMA reset 完成
gt_rxpmaresetdone[3:0] 每条 lane RX PMA reset 完成

如果 link_up=0，先看这个 probe。
常见问题：

powergood 不全 1：GTY primitive 或电源/时钟问题
txresetdone=0：TX userclk/refclk/reset sequence 问题
rxresetdone=0：RX CDR 没锁、没有输入信号、线没接对
rxpmaresetdone 某 lane=0：对应 lane 物理链路或 CDR 有问题

probe2: state

.probe2(state)

含义：selftest FSM 当前状态。

根据你之前代码，大概是：

ST_WAIT_LINK 等待 link_up
ST_START 发起一个 packet
ST_PAYLOAD 发送 payload beat
ST_WAIT_RX 等待收到 packet
ST_GAP 包间隔

判断：

卡在 ST_WAIT_LINK：GTY/link 没起来
卡在 ST_START：packetizer 不 ready
卡在 ST_PAYLOAD：payload ready/valid 卡住
卡在 ST_WAIT_RX：发出去了但没收到
一直循环 ST_START/ST_PAYLOAD/ST_WAIT_RX/ST_GAP：链路在跑

probe3: TX/RX/selftest 关键事件

.probe3({
tx_start_valid,
tx_start_ready,
tx_payload_tvalid,
tx_payload_tready,
rx_payload_valid,
rx_packet_done,
rx_crc_ok,
rx_format_error,
payload_seen_for_packet,
payload_match_for_packet,
payload_mismatch_seen,
packet_done_seen
})

含义：一组握手、收包、CRC、payload 检查状态。

字段解释：

tx_start_valid selftest 请求开始发一个 packet
tx_start_ready packetizer 可以接受 start
tx_payload_tvalid selftest 正在提供 payload
tx_payload_tready packetizer 可以接收 payload
rx_payload_valid depacketizer 输出了 payload beat
rx_packet_done depacketizer 收完一个 packet
rx_crc_ok 当前 packet CRC 正确，通常可能是脉冲
rx_format_error packet 格式错误
payload_seen_for_packet 本 packet 曾经看到 payload
payload_match_for_packet payload 内容匹配 expected_token_id
payload_mismatch_seen 曾经看到 payload 不匹配
packet_done_seen 曾经收到完整 packet，通常是 latched

重点看：

tx_start_valid & tx_start_ready 同时为 1：开始发包成功
tx_payload_tvalid & tx_payload_tready 同时为 1：payload 被接受
rx_payload_valid 拉高：RX 真的吐出 payload
rx_packet_done 拉高：完整包收到
rx_crc_ok 拉高：CRC 正确
rx_format_error 拉高：PCS/packet 格式有问题
payload_mismatch_seen 拉高：payload 内容错

验收时希望：

selftest_errors_r == 0

probe8: tx_token_id

.probe8(tx_token_id)

含义：TX 当前准备发送的 token 值。

用于检查发送序列是否递增。
每成功完成一个 packet 后通常加 1。

probe9: expected_token_id

.probe9(expected_token_id)

含义：RX checker 期望收到的 token 值。

在内部 loopback 或一发一收设计中，它应该和收到的 rx_payload_data[63:0] 对齐。

如果做双 FPGA A/B 互联，要注意：A 收到的是 B 发的 token，B 收到的是 A 发的 token。此时 expected_token_id 不能还按“自己发自己收”的假设，否则会误报。

probe10: rx_payload_data[63:0]

.probe10(rx_payload_data[63:0])

含义：RX payload 低 64 bit。

当前 selftest 里 TX payload 是：

tx_payload_tdata = {576’h0, tx_token_id};

所以 RX 正常时：

rx_payload_data[63:0] == expected_token_id

如果 CRC 对但 payload 不对，要看这个值。

probe11: rx_payload_keep

.probe11(rx_payload_keep)

含义：RX payload 每个 byte 是否有效，80 bit 对应 640 bit data。

当前 NEXT_TOKEN 只有 8 字节，所以期望：

rx_payload_keep = 80’h0000_0000_0000_0000_00ff

如果 keep 不对，可能是 packet length、depacketizer、PCS 对齐或 tkeep 处理问题。

probe12: RX packet header 摘要

.probe12({
rx_packet_type,
rx_src_lpu,
rx_dst_lpu,
rx_stream_id,
rx_request_id,
rx_payload_bytes,
rx_payload_beat_index
})

含义：收到 packet 的关键 header 字段。

字段：

rx_packet_type 包类型，比如 PKT_NEXT_TOKEN
rx_src_lpu 源 LPU ID
rx_dst_lpu 目的 LPU ID
rx_stream_id stream 类型
rx_request_id request 序号
rx_payload_bytes payload 字节数
rx_payload_beat_index 当前 payload beat index

当前 NEXT_TOKEN 期望大概是：

rx_packet_type = PKT_NEXT_TOKEN
rx_src_lpu = 8’h01
rx_dst_lpu = 8’h02
rx_stream_id = STREAM_CONTROL
rx_payload_bytes = 8
beat_index = 0

双端互联时 A/B 的 src/dst 要反过来检查。

probe13: PCS debug

.probe13({
dbg_pcs_frame_lock,
dbg_pcs_frames_sent,
dbg_pcs_data_frames_sent,
dbg_pcs_frames_received,
dbg_pcs_data_frames_received,
dbg_pcs_frame_format_errors
})

含义：PCS 层状态。

字段：

dbg_pcs_frame_lock PCS 是否找到 frame marker / lane alignment
dbg_pcs_frames_sent PCS 总发送 frame 数
dbg_pcs_data_frames_sent PCS 发送 data frame 数
dbg_pcs_frames_received PCS 总接收 frame 数
dbg_pcs_data_frames_received PCS 接收 data frame 数
dbg_pcs_frame_format_errors PCS frame 格式错误计数

判断：

frame_lock=0：
RX 没看到有效 PCS marker，可能物理链路/极性/lane map/bit alignment 问题

frames_sent 增长但 frames_received 不增长：
TX 在发，但 RX PCS 没收到有效 frame

frames_received 增长但 format_errors 增长：
收到东西了，但格式错，常见是 lane 顺序、bit slip、PCS framing 问题

probe14: loopback/reset 配置

.probe14({GT_LOOPBACK_MODE, rst_n, reset_in})

含义：确认当前 bitstream 到底在什么模式、reset 是否释放。

字段：

GT_LOOPBACK_MODE GTY loopback 配置
rst_n 内部同步后的低有效复位释放信号
reset_in 外部 reset 输入

重点：

GT_LOOPBACK_MODE = 12’h000 外部正常链路
GT_LOOPBACK_MODE = 12’h492 4 lane near-end PMA loopback，即 {4{3’b010}}
rst_n = 1 系统已释放 reset
reset_in = 0 外部没有按住 reset

如果你想验证 PCB 片间链路，必须看到：

GT_LOOPBACK_MODE == 12’h000

否则数据没有真正走外部 PCB。

调试时推荐观察顺序

  1. probe14：确认 reset 释放、loopback 模式正确
  2. probe1/probe0：确认 GTY ready、link_up
  3. probe13：确认 PCS frame_lock
  4. probe3：确认 TX handshake 和 RX packet_done
  5. probe4/probe5/probe6：确认包计数增长
  6. probe10/probe11/probe12：确认 payload/header 正确
  7. probe7：最终确认 error 不增长

最理想的稳定状态是：

link_up = 1
GT resetdone/pmaresetdone 全 1
state 周期性跑动
packets_sent 持续增长
packets_received 持续增长
pcs_frame_lock = 1
rx_crc_ok 周期性脉冲
selftest_errors_r = 0

它适合验证：

  • 多 FPGA / 多板之间的 RTL 通信协议、包格式、CRC、流控、复位恢复、链路训练、吞吐和延迟。
  • 用 HT3 并行互连或 ProtoCompiler HSTDM 做宽总线跨 FPGA 分割验证。
  • 用 MGB/GTH SerDes 做更接近高速串行片间链路的 FPGA 原型验证。

它不等价于真实 ASIC/Chiplet 的物理层验证，不能证明最终硅片 PHY、封装 SI、CDR/PLL、均衡、眼图、串扰、电源完整性等模拟/板级问题。

  • 当前 lpu_link_mac_pcs640_gty4x160 是 packetizer -> PCS TX -> GTY PMA -> PCS RX -> depacketizer，协议层很适合作为片间链路验证核心。serdes/rtl/lpu_link/lpu_link_mac_pcs640_gty4x160.sv:1

  • HAPS-80 是 XCVU440 GTH，不是 GTY；如果走 MGB/SATA，线速大概率要降到 6Gb/s/lane 级别，并重新生成 UltraScale GTH IP、重做 wrapper/TSS/XDC。

建议路径：

  1. 如果你要验证“协议/RTL 是否能跨片工作”，优先用 HAPS-80 HT3 + ProtoCompiler 分割。把两个 chiplet/LPU endpoint 放到不同 FPGA，通过 HT3/HSTDM 或固定 inter-FPGA bus 连接，验证包、CRC、序号、流控、复位恢复。

  2. 如果你要验证“SerDes 型片间通信协议”，走 HAPS-80 MGB/GTH。复用现有 LPU PCS/packet/depacketizer，把 PMA wrapper 从 VCU118 GTY 改成 HAPS-80 XCVU440 GTH，先做内部 loopback，再做 FPGA A 到 FPGA D / 两系统间 SATA
    crossover 外部链路。

  3. 验证指标至少包括：link_up、pcs_frame_lock、TX/RX packet counter、CRC error、format error、sequence gap、payload mismatch、reset/retrain 次数、长跑错误率、不同包型覆盖率。

所以答案是：能实现你的片间通信验证，但应定位为 FPGA 原型级链路/协议验证。若目标是 ASIC 最终物理层 signoff，还需要真实 SerDes PHY、封装/板级 SI、实验室仪器和硅后验证补齐。
